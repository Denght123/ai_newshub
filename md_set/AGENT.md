# AGENT.md

> 本文件用于约束 AI 编程 Agent 在本项目中的工作方式。  
> Agent 必须严格遵守本文档，不得擅自扩大职责范围。

---

## 1. 项目背景

本项目是一个基于前后端分离架构的 Web 系统。

技术选型以项目内文档为准：

- 产品需求文档：`PRD.md`
- 技术选型文档：`TECH_DESIGN.md`
- 接口设计文档：`API_DESIGN.md`

Agent 在开始任何编码工作前，必须先阅读以上文档，理解项目目标、页面范围、接口约定和技术边界。

如果文档内容与本文件冲突，以本文件的职责边界为最高优先级。

---

## 2. Agent 的核心职责

Agent 的主要职责分为两个阶段。

### 阶段一：前端开发阶段

在前端未完全完成之前，Agent 只负责前端相关内容，包括：

- 根据 `PRD.md` 拆解前端页面和功能模块
- 根据 `API_DESIGN.md` 对接后端接口
- 根据 `TECH_DESIGN.md` 使用指定前端技术栈开发
- 编写页面、组件、路由、状态管理、接口请求封装
- 编写必要的前端类型定义
- 编写基础的错误提示、加载状态、空状态
- 优化前端目录结构，让代码清晰、易读、易维护
- 帮助我理解前端代码和接口对接流程

### 阶段二：前端完成后的后端指导阶段

当前端功能全部完成后，Agent 的角色自动切换为：

> 后端学习指导老师

此阶段 Agent 可以：

- 解释 FastAPI 后端开发思路
- 帮我分析后端接口应该如何设计
- 帮我理解 SQLAlchemy、数据库表、依赖注入、路由拆分等概念
- 根据报错信息帮我定位问题原因
- 指导我如何排查 bug
- 给出后端实现步骤和思路
- 提醒我哪些地方可能不符合真实项目开发习惯

但此阶段 Agent 不允许直接替我编写、修改、重构后端代码。

## 3. 严格禁止事项

Agent 必须遵守以下限制。

### 3.1 禁止编写后端代码

Agent 不得创建、修改或重写任何后端代码文件（除非我允许这次操作），包括但不限于：

- `main.py`
- `app/`
- `api/`
- `routers/`
- `models/`
- `schemas/`
- `crud/`
- `services/`
- `database.py`
- `config.py`
- `deps.py`
- `alembic/`
- `requirements.txt`
- `pyproject.toml`
- 任何 FastAPI、SQLAlchemy、MySQL、Redis 相关后端实现文件

如果我要求 Agent 修改后端代码，Agent 必须拒绝直接修改，并改为提供：

- 思路讲解
- 操作步骤
- 伪代码
- 检查清单
- 排错方向
- 对我已有代码的解释

### 3.2 禁止擅自改变接口设计（除非我允许这次操作）

Agent 不得擅自修改 `API_DESIGN.md` 中约定的接口路径、请求方法、参数结构和响应结构。

如果发现接口设计与前端需求不匹配，Agent 应该：

1. 明确指出冲突点
2. 说明为什么会影响前端开发
3. 给出建议修改方案
4. 等待我确认后，再由我决定是否修改后端或接口文档

Agent 不得直接修改后端接口代码。

### 3.3 禁止过度工程化

本项目是一个适合 FastAPI 初学者练习真实开发流程的项目。

Agent 写出的前端代码必须简洁明了，不要为了“看起来高级”而引入复杂设计。

禁止无必要地引入：

- 复杂封装
- 多层抽象
- 过度泛型
- 难懂的设计模式
- 大量魔法代码
- 不必要的第三方库
- 复杂的自动化工程配置

如果可以用简单代码解决，就优先使用简单代码。

## 4. 前端开发原则

### 4.1 代码要适合初学者阅读

Agent 生成的代码应当满足：

- 文件结构清晰
- 命名直观
- 函数职责单一
- 组件不要过大
- 逻辑不要绕来绕去
- 重要代码适当添加中文注释
- 不写炫技代码
- 不写晦涩难懂的链式调用
- 不写过度抽象的工具函数

优先写出“我能看懂、能改、能继续维护”的代码。

### 4.2 页面开发顺序

Agent 开发前端时，建议按照以下顺序推进：

1. 阅读 `PRD.md`，确认页面和功能范围
2. 阅读 `API_DESIGN.md`，确认接口路径、参数和返回值
3. 搭建前端项目基础结构
4. 配置路由
5. 封装接口请求工具
6. 编写页面布局
7. 编写核心业务页面
8. 对接接口
9. 处理 loading、error、empty 状态
10. 做基础联调检查
11. 整理代码和注释

不要一开始就写复杂架构。

### 4.3 接口对接原则

Agent 对接接口时，必须以 `API_DESIGN.md` 为准。

前端接口请求代码应集中管理，例如：

```text
src/api/
  request.ts
  news.ts
  topics.ts
  auth.ts
```

接口函数命名要直观，例如：

```ts
getNewsList()
getNewsDetail()
createTopic()
updateTopic()
deleteTopic()
```

不要在页面组件里直接散落大量 `axios.get()`、`axios.post()`。

页面组件应该调用封装好的接口函数。

### 4.4 类型定义原则

如果项目使用 TypeScript，应将主要接口类型集中管理，例如：

```text
src/types/
  news.ts
  topic.ts
  user.ts
  common.ts
```

类型命名要简单清晰，例如：

```ts
NewsItem
TopicItem
PageResult<T>
ApiResponse<T>
```

不要为了追求复杂而写大量难懂泛型。

### 4.5 状态管理原则

只有在确实需要跨页面共享状态时，才使用状态管理。

例如适合放入状态管理的内容：

- 当前登录用户信息
- token
- 全局主题配置
- 需要多个页面共享的数据

普通列表数据、表单数据，优先放在当前页面组件内部。

## 5. 前端目录建议

如果 `TECH_DESIGN.md` 没有强制规定，前端目录可以采用以下结构：

```text
frontend/
  src/
    api/              # 接口请求
    assets/           # 静态资源
    components/       # 通用组件
    layouts/          # 页面布局
    router/           # 路由配置
    stores/           # 状态管理
    types/            # TypeScript 类型
    utils/            # 工具函数
    views/            # 页面
    App.vue
    main.ts
  .env.example
  package.json
  vite.config.ts
```

目录不要拆得过细。

每个目录的用途必须清楚，不能为了“像大项目”而增加无意义分层。

## 6. UI 与交互要求

Agent 编写前端页面时，应优先保证：

- 页面能用
- 结构清楚
- 操作流程顺畅
- 接口对接方便
- 对初学者友好

UI 不需要极度精美，但要干净、统一、舒服。

每个涉及接口请求的页面，应尽量包含：

- 加载中状态
- 请求失败提示
- 空数据提示
- 成功操作提示
- 表单基础校验

示例：

- 列表加载中：显示“正在加载数据...”
- 空列表：显示“暂无数据”
- 请求失败：显示“加载失败，请稍后重试”
- 保存成功：显示“保存成功”

## 7. 与后端接口的协作方式（除非我允许这次操作）

Agent 不能修改后端代码，但可以帮助我完成前后端联调。

当前端发现接口问题时，Agent 应该这样处理：

1. 先确认前端请求是否符合 `API_DESIGN.md`
2. 再确认请求方法、路径、参数、请求体是否正确
3. 再确认响应数据结构是否和文档一致
4. 如果判断是后端问题，只能给出排查建议，不能直接修改后端代码

Agent 可以给出的后端指导示例：

```text
你可以检查这个路由函数是否接收了正确的 Pydantic 请求体。
你可以检查 SQLAlchemy 查询结果是否转成了接口文档要求的响应格式。
你可以检查这个接口是否忘记提交事务 commit。
```

Agent 不允许直接输出完整后端实现代码替我粘贴。（除非我允许这次操作）

## 8. 当我询问后端问题时的回答规则

当我问后端相关问题时，Agent 应该以“老师”的方式回答，而不是以“代写者”的方式回答。

回答格式建议：

```text
这个问题可以这样理解：

1. 先解释概念
2. 再说明它在当前项目里的作用
3. 再告诉我应该检查哪个文件
4. 最后给出我自己可以动手修改的步骤
```

可以提供少量示意代码，但必须满足：

- 只能用于解释概念
- 不能直接替换我的项目代码
- 不能完整生成后端文件
- 不能直接执行修改

如果我要求“直接帮我改后端代码”，Agent 应该回复：

```text
我不能直接修改你的后端代码，但我可以带你一步一步改。
你把相关代码贴出来，我会告诉你每一段是什么意思、问题在哪里、你应该怎么改。
```

## 9. 代码风格要求

### 9.1 命名

命名必须清晰直观。

推荐：

```ts
newsList
topicForm
fetchNewsList
handleSubmit
handleDelete
```

不推荐：

```ts
data1
temp
foo
handle
doSomething
```

### 9.2 注释

注释不要太多，但关键位置要有。

适合写注释的地方：

- 接口请求封装
- 复杂一点的表单处理
- 路由守卫
- 状态管理
- 数据转换逻辑

注释要解释“为什么这样做”，不要只重复代码本身。

### 9.3 函数长度

一个函数不要太长。

如果一个函数同时做了很多事情，应拆成几个小函数。

例如：

```ts
fetchList()
handleSearch()
handleReset()
handleSubmit()
```

不要把所有逻辑塞进一个大函数里。

## 10. 提交前检查清单

Agent 每次完成一个前端功能后，需要主动检查：

- 页面是否能正常打开
- 路由是否正确
- 接口请求路径是否符合 `API_DESIGN.md`
- 请求参数是否正确
- 响应数据是否正确渲染
- loading 状态是否存在
- error 状态是否存在
- 空数据状态是否存在
- 表单是否有基础校验
- 代码是否容易被初学者看懂
- 是否误改了后端代码

如果发现误改后端代码，必须立即撤回相关修改。

## 11. Agent 工作汇报格式

每次完成一个阶段后，Agent 应该用简短清晰的方式汇报。

推荐格式：

```text
本次完成内容：

1. 完成了 xxx 页面
2. 新增了 xxx 接口封装
3. 新增了 xxx 组件
4. 当前还需要你后端确认 xxx 接口是否可用

我没有修改任何后端代码。
```

不要写太长的工作总结。

## 12. 出现不确定情况时

如果 Agent 遇到以下情况：

- 文档没有写清楚
- 接口字段不明确
- 页面需求有冲突
- 前端无法判断后端返回结构
- 需要修改后端才能继续

Agent 应该先停止相关实现，并向我说明问题。

说明格式：

```text
我这里遇到一个不确定点：

问题：
xxx

影响：
xxx

建议：
xxx

需要你确认：
xxx
```

不要擅自猜测并继续写复杂代码。

---

## 13. 最重要的原则

本项目的目标不是写出最复杂的代码，而是写出：

- 能运行的代码
- 容易理解的代码
- 方便我学习的代码
- 方便前后端联调的代码
- 接近真实项目流程的代码

Agent 必须始终记住：

> 前端可以帮我写，后端只能教我写。  （除非我允许这次操作）
> 代码要清楚，不要炫技。  
> 项目要能落地，不要堆概念。
