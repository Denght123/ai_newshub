## 2. 产品定位

AI NewsHub 是一个面向内容创作者的轻量级 AI 资讯管理后台。

它解决的问题不是“自动写文章”，而是把散落在各处的 AI 新闻、产品发布、模型动态、开源项目、行业事件统一管理起来，并沉淀成可跟进的公众号选题。

系统第一版重点做三件事：

1. 管理 AI 资讯素材；
2. 将有价值的资讯转化为公众号选题；
3. 用状态流管理选题从“待评估”到“已发布”的过程。

第一版不追求复杂自动化，核心目标是做出一个真实可用、结构规范、可以上线的小型后台系统。

## 3. 使用场景

### 3.1 资讯收集场景

用户看到一条 AI 相关新闻，例如模型发布、开源项目、产品更新、行业事件。

用户进入后台，手动录入资讯：

- 标题；
- 来源；
- 原文链接；
- 摘要；
- 分类；
- 标签；
- 热度分；
- 重要程度。

录入后，这条资讯进入资讯库，后续可以搜索、筛选、收藏或转为选题。

### 3.2 选题管理场景

用户发现某条资讯值得写成公众号文章。

用户点击“加入选题池”，填写：

- 选题标题；
- 写作角度；
- 推荐公众号标题；
- 选题价值；
- 传播潜力；
- 写作难度；
- 计划发布时间。

之后选题会经历：

```text
待评估 → 已选中 → 写作中 → 已发布
```

也可能被放弃：

```text
待评估 → 已放弃
写作中 → 已放弃
```

### 3.3 内容规划场景

用户打开仪表盘，快速看到：

- 当前有多少资讯；
- 有多少未读资讯；
- 有多少选题待评估；
- 有多少选题正在写；
- 最近新增的资讯和选题。

这样可以辅助用户决定接下来写什么。

## 4. 用户角色

第一版只设计两个角色，避免复杂权限系统。

| 角色 | 说明 |
|---|---|
| 普通用户 | 可以管理自己创建的资讯和选题 |
| 管理员 | 可以管理所有资讯、选题、分类和标签 |

第一版不做组织、团队、多人协作、审批流。

| 模块 | 功能 |
|---|---|
| 用户认证 | 注册、登录、获取当前用户、JWT 鉴权 |
| 分类管理 | 创建分类、分类列表、修改分类、删除分类 |
| 标签管理 | 创建标签、标签列表、修改标签、删除标签 |

| 选题管理 | 新建、从资讯创建、列表、详情、修改、删除、状态流转、搜索、筛选、分页 |
| 仪表盘 | 基础统计、最近资讯、最近选题 |
| 工程化 | 环境变量、统一响应、统一异常、数据库迁移、Docker 部署 |

## 5.2 第一版可以不做

| 功能 | 不做原因 |
|---|---|
| 自动爬虫 | 会增加反爬、定时任务、数据清洗复杂度 |
| AI 自动生成文章 | 会引入大模型 API、提示词、成本控制 |
| 富文本编辑器 | 前端复杂度较高 |
| 多人协作 | 权限和数据隔离复杂度上升 |
| 审核流 | 第一版不需要 |
| 文件上传 | 可以后续扩展 |
| GitHub Actions | 可作为后续工程化增强 |
| 消息队列 | 当前业务量不需要 |

## 7. 业务模块需求

## 7.1 用户认证模块

### 7.1.1 注册

用户可以通过用户名、邮箱、密码注册账号。

规则：

1. 用户名不能为空；
2. 用户名不能重复；
3. 邮箱不能为空；
4. 邮箱不能重复；
5. 密码长度不能少于 6 位；
6. 密码必须加密存储；
7. 默认角色为普通用户。

### 7.1.2 登录

用户可以通过用户名或邮箱加密码登录。

登录成功后返回：

1. access_token；
2. token_type；
3. 当前用户基本信息。

### 7.1.3 获取当前用户

前端携带 token 请求 `/auth/me`，后端返回当前用户信息。

### 7.1.4 权限判断

规则：

1. 未登录用户不能访问后台接口；
2. 普通用户只能操作自己创建的资讯和选题；
3. 管理员可以操作所有数据；
4. 分类和标签的新增、修改、删除仅管理员可操作；
5. 分类和标签的列表查询登录用户可操作。

---

## 7.2 分类模块

分类用于给资讯和选题做一级归类。

建议默认分类：

| 分类名 | 说明 |
|---|---|
| 大模型 | GPT、Claude、Gemini、DeepSeek 等 |
| AI 绘画 | 图像生成、视频生成、设计工具 |
| Agent | 智能体、自动化工具、编程助手 |
| 开源项目 | GitHub、HuggingFace 等开源动态 |
| 国产 AI | 国内大模型和 AI 产品 |
| 行业应用 | 教育、办公、医疗、金融等 |
| 商业融资 | 融资、收购、估值、公司动态 |
| 政策监管 | AI 法规、版权、合规事件 |

分类字段：

| 字段 | 说明 |
|---|---|
| name | 分类名称 |
| description | 分类描述 |
| sort_order | 排序值 |
| is_active | 是否启用 |

## 7.4 资讯模块

资讯是系统的核心素材。

### 7.4.1 资讯字段

| 字段 | 说明 |
|---|---|
| title | 资讯标题，必填 |
| source_name | 来源名称 |
| source_url | 原文链接 |
| summary | 简短摘要 |
| content | 详细内容或个人笔记 |
| category_id | 分类 ID |
| tag_ids | 标签 ID 列表 |
| status | 资讯状态 |
| importance_score | 重要程度，1-5 |
| heat_score | 热度，1-5 |
| is_favorite | 是否收藏 |
| publish_time | 原文发布时间 |

### 7.4.2 资讯状态

| 状态 | 说明 |
|---|---|
| unread | 待阅读 |
| read | 已阅读 |
| added_to_topic | 已加入选题 |
| ignored | 已忽略 |

收藏使用 `is_favorite` 单独表示，不放入 status，避免状态混乱。

### 7.4.3 资讯列表能力

资讯列表必须支持：

1. 分页；
2. 关键词搜索；
3. 分类筛选；
4. 状态筛选；
5. 收藏筛选；
6. 按创建时间倒序；
7. 按发布时间倒序；
8. 按热度分排序；
9. 按重要程度排序。

### 7.4.4 软删除

资讯删除建议使用软删除。

规则：

1. 删除时不直接删除数据库记录；
2. 将 `is_deleted` 设置为 true；
3. 列表查询默认不返回已删除数据。

---

## 7.5 选题模块

选题是从资讯沉淀出的写作任务。

### 7.5.1 选题字段

| 字段 | 说明 |
|---|---|
| news_id | 关联资讯 ID，可为空 |
| title | 选题标题，必填 |
| angle | 写作角度 |
| recommended_title | 推荐公众号标题 |
| reason | 为什么值得写 |
| target_reader | 目标读者 |
| category_id | 分类 ID |
| status | 选题状态 |
| value_score | 选题价值，1-5 |
| difficulty_score | 写作难度，1-5 |
| traffic_score | 传播潜力，1-5 |
| deadline | 计划发布时间 |

### 7.5.2 选题状态

| 状态 | 说明 |
|---|---|
| pending | 待评估 |
| selected | 已选中 |
| writing | 写作中 |
| published | 已发布 |
| abandoned | 已放弃 |

### 7.5.3 状态流转规则

允许：

```text
pending → selected
selected → writing
writing → published
pending → abandoned
selected → abandoned
writing → abandoned
```

第一版不强制限制状态流转，可以先在业务文档中约定，后端允许直接修改状态。第二版再加严格校验。

### 7.5.4 从资讯创建选题

用户可以从资讯详情页点击“加入选题池”。

后端处理逻辑：

1. 判断资讯是否存在；
2. 判断当前用户是否有权限查看该资讯；
3. 创建选题；
4. 选题关联 news_id；
5. 将资讯状态改为 `added_to_topic`；
6. 返回创建后的选题。

## 7.6 仪表盘模块

仪表盘第一版只做轻量统计。

### 7.6.1 统计项

| 指标 | 说明 |
|---|---|
| news_total | 资讯总数 |
| unread_news_total | 未读资讯数 |
| favorite_news_total | 收藏资讯数 |
| topic_total | 选题总数 |
| pending_topic_total | 待评估选题数 |
| writing_topic_total | 写作中选题数 |
| published_topic_total | 已发布选题数 |

### 7.6.2 最近数据

返回：

1. 最近 5 条资讯；
2. 最近 5 条选题。

### 7.6.3 Redis 缓存规则

仪表盘统计可以缓存 60 秒。

原因：

1. 首页访问频率高；
2. 统计查询会重复执行；
3. 60 秒内轻微延迟可以接受。

## 8. 非功能需求

## 8.1 性能要求

1. 所有列表接口必须分页；
2. 默认每页 10 条；
3. 最大每页 100 条；
4. 高频查询字段建立索引；
5. Dashboard 统计使用 Redis 短缓存；
6. 单接口响应时间本地环境建议小于 500ms。

## 8.2 安全要求

1. 密码必须哈希存储；
2. JWT 密钥放在环境变量；
3. 生产环境不能使用默认密钥；
4. 修改和删除必须校验数据归属；
5. 管理员接口必须校验角色；
6. 不在接口响应中返回 hashed_password；
7. CORS 只允许指定前端域名；
8. `.env` 不提交到 Git。

## 8.3 可维护性要求

1. 使用分层目录结构；
2. 路由层不直接写复杂业务；
3. 数据库操作放到 CRUD 层；
4. 业务判断放到 Service 层；
5. 请求和响应使用 Pydantic Schema；
6. 异常响应格式统一；
7. 代码格式统一；
8. README 写清楚启动和部署方式。
