# AI NewsHub PRD

## 1. 产品定位

AI NewsHub 不再定位为传统“资讯管理后台”，而是一个面向个人内容创作者和 AI 学习者的 **AI 资讯自动采集 + RAG 知识库 + 问答检索系统**。

核心目标只有一句话：

```text
每天自动抓取 AI 资讯，沉淀到知识库，以后可以按日期和问题准确查回。
```

V1 不追求复杂 CMS，也不把“手动管理资讯、选题池、分类标签”作为主流程。那些能力可以保留为后续管理工具，但不应该占据主页面。

---

## 2. 用户真正要完成的事

用户每天打开系统，只需要完成三件事：

1. 点击一次“采集今日 AI 资讯”；
2. 看今日摘要和入库结果；
3. 向 AI 提问，例如“今天有哪些 AI 消息？”“2026-06-03 DeepSeek 有什么动态？”。

系统回答时必须基于本地 RAG 知识库，不允许凭空编造。

---

## 3. V1 核心页面

| 页面 | 作用 |
|---|---|
| 每日采集 | 触发固定 skill 流程，抓取当日 AI 资讯，生成摘要并写入知识库 |
| 知识库 | 按日期查看已入库资讯，检查来源、发布时间、摘要和入库状态 |
| AI 问答 | 用户提问，后端检索 RAG 知识库，大模型基于检索片段流式回答 |

旧页面处理策略：

| 旧页面 | V1 处理 |
|---|---|
| 资讯管理 | 不作为主入口，后续可做“高级管理” |
| 选题池 | 由 AI 问答里的“选题推荐”能力替代 |
| 分类与标签 | V1 不要求用户手动维护分类 |
| 仪表盘 | 改造成“每日采集概览” |

---

## 4. 固定 AI 抓取 Skill 流程

后端需要把抓取流程固定下来，而不是让用户面对一堆配置项。

V1 固定流程：

```text
1. 确定日期窗口，例如 today / 指定日期
2. 读取固定 AI 资讯源
3. 抓取 RSS / API / 页面摘要
4. 记录失败来源
5. 对候选内容去重
6. 调用 OpenAI-compatible 大模型整理成结构化 JSON
7. 写入 knowledge_documents
8. 将正文切分成 rag_chunks
9. 后续生成 embedding 并写入向量字段或向量库
10. 返回本次采集摘要
```

前端只暴露少量参数：

| 参数 | 是否需要展示 |
|---|---|
| 采集日期 | 展示 |
| 最大条数 | 展示 |
| dry_run | 展示 |
| api_base_url / api_key / model | 可折叠到“模型设置” |
| 来源细节 | 不展示，后端固定 |

---

## 5. RAG 知识库目标

知识库不是简单列表，而是为了“以后可以准确问答”。

每条入库资讯必须保留：

| 字段 | 说明 |
|---|---|
| title | 标题 |
| summary | 一句话摘要 |
| content | 可用于 RAG 的正文 |
| source_name | 来源名称 |
| source_url | 来源链接 |
| published_at | 原文发布时间 |
| digest_date | 归档日期 |
| credibility | 来源可信度，例如 official/media/community/paper |
| created_at | 入库时间 |

每条资讯会被切成多个知识片段：

| 字段 | 说明 |
|---|---|
| document_id | 对应知识文档 |
| chunk_text | 片段文本 |
| chunk_index | 片段顺序 |
| embedding | 向量，V1 可先预留字段 |
| digest_date | 方便按日期过滤 |

---

## 6. AI 问答目标

用户可以问：

```text
今天的 AI 消息是什么？
昨天有哪些模型发布？
2026-06-03 DeepSeek 有什么动态？
最近 7 天有哪些适合写公众号的选题？
```

后端流程：

```text
1. 接收问题和日期范围
2. 从 rag_chunks 检索相关片段
3. 把片段和问题组成 prompt
4. 调用 OpenAI-compatible 大模型
5. 使用 StreamingResponse 流式返回
6. 同时返回引用来源
```

回答要求：

1. 必须基于检索结果；
2. 回答中说明消息日期；
3. 重要结论附来源；
4. 如果知识库没有相关内容，明确说“知识库中没有找到”；
5. 不再次联网搜索，不凭空补充。

## 7. V1 必做范围

| 模块 | 必做内容 |
|---|---|
| 认证 | 注册、登录、获取当前用户、JWT |
| 每日采集 | 创建采集任务、返回任务摘要、预留固定 skill 流程 |
| 知识库 | 文档列表、日期筛选、文档详情、RAG chunk 预留 |
| AI 问答 | 普通问答接口、流式问答接口、引用来源结构 |
| 文档 | PRD、API、数据库设计与开发步骤 |
| 前端 | 三个主页面：每日采集、知识库、AI 问答 |

---

## 8. V1 暂不做

| 功能 | 原因 |
|---|---|
| 手动维护分类标签 | 对核心目标帮助不大 |
| 已读 / 未读 / 收藏 | 更像个人 CMS，暂不作为主线 |
| 复杂选题状态流 | 用 AI 问答生成选题建议即可 |
| 多用户协作 | 增加权限复杂度 |
| 后台可视化大屏 | 与 RAG 主目标无关 |
| 自动公开发布文章 | 有内容安全和平台风险 |

## 9. 一个月学习开发路线

### 第 1 阶段：接口和页面收敛

```text
1. 保留登录认证
2. 重构前端为三页
3. 新增 daily-digest / knowledge / rag-chat 接口占位
4. Swagger 能看到新的清晰接口
```

### 第 2 阶段：知识库表与入库

```text
1. 写 knowledge_documents ORM
2. 写 rag_chunks ORM
3. 用 Alembic 建表
4. 将抓取结果写入 knowledge_documents
5. 将内容切分后写入 rag_chunks
```

### 第 3 阶段：RAG 检索

```text
1. 先用 MySQL like 做最小检索
2. 再接 embedding 模型
3. 存向量
4. 做 top_k 相似片段检索
```

### 第 4 阶段：流式问答

```text
1. 后端 StreamingResponse
2. 前端 fetch ReadableStream
3. 显示逐字输出
4. 展示引用来源
```

---

## 10. 最终验收标准

```text
[ ] 用户可以登录
[ ] 用户可以点击“采集今日 AI 资讯”
[ ] 采集结果可以写入知识库
[ ] 用户可以按日期查看知识库内容
[ ] 用户可以询问某一天或某段时间的 AI 资讯
[ ] AI 回答基于知识库检索结果
[ ] 回答能显示来源和日期
[ ] 流式输出可用
[ ] 前端主流程只有每日采集、知识库、AI 问答三块
```
